# 關卡設計流程

本文件說明《寶島風情畫》新增或調整關卡時的標準流程。關卡的可編輯來源是 `docs/levelN.md`；`js/levelData.js` 是由工具產生的執行資料，不應直接手動修改。

## 1. 先定義關卡主題

每一關先確定三件事：

1. 場景主題：例如台北遠景、淡水夕照或新竹科學園區。
2. 關卡魔王：決定外型、攻擊意象與 Boss 名稱。
3. 關卡節奏：安排普通敵人、地形、陷阱與砲塔，讓玩家在進入 Boss 戰前逐步學會本關的危險。

目前的共用規格以 800×480 的遊戲視窗、60×60 的地圖格，以及約 99 欄的水平關卡為基準。設計時要確保玩家在每個畫面都至少有一條可辨識的移動路徑，並預留閃避敵彈與地形碰撞的空間。

## 2. 以地圖草稿安排節奏

關卡地圖使用 Markdown 裡的 Unicode 方框繪製。每一行必須以 `│` 開頭與結尾，整張地圖放在 fenced code block 中。例如：

```text
┌───────────────────────────────────────────────────────────────────────────────┐
│       eeeee                 x          塔                         ┌──────┐    │
│  ->        s          x               |                          │ boss │    │
│       eeeee                 x          塔                         └──────┘    │
└───────────────────────────────────────────────────────────────────────────────┘
```

建議由左至右分成四個節奏區段：

| 區段 | 設計目的 | 常用元素 |
| --- | --- | --- |
| 起始區 | 讓玩家熟悉場景與操作 | 起始點、少量 `x`、低密度地形 |
| 教學區 | 引入本關特色危險 | `s`、`|`、單側 `塔` |
| 壓力區 | 混合多種威脅，測試玩家反應 | `e`、`x`、`s`、陷阱、砲塔 |
| Boss 區 | 收束捲軸並準備頭目戰 | Boss 方框與必要的砲塔 |

不要只把敵人平均散布在地圖上。每一段應該有「辨識危險 → 做出選擇 → 獲得喘息」的循環；連續高壓區之後要留出沒有新威脅的空間。

## 3. 使用地圖符號配置物件

目前 `scripts/parse_levels.py` 會解析下列符號：

| 符號 | 物件 | 設計用途 |
| --- | --- | --- |
| `->` | 玩家起始點 | 每關至少放置一個；通常位於左側中段 |
| `e` | 固體地形 | 阻擋玩家與子彈，製造通道、掩體與夾角 |
| `x` | 巡航敵機 | 主要空中敵人，適合放在開闊區或交錯路徑 |
| `s` | 背刺敵人 | 讓玩家不能只盯著前方，應避免連續密集觸發 |
| `|` | 下墜陷阱 | 放在玩家可能經過的上方，搭配預警與閃避空間 |
| `塔` | 砲塔 | 放在地形或邊界附近，形成固定角度的火力壓力 |
| `b` / `B` | 炸彈道具 | 由地圖預先放置一個炸彈補給 |
| `p` / `P` | 武器道具 | 由地圖預先放置一個武器升級 |
| `h` / `H` | 護盾道具 | 由地圖預先放置一個護盾補給 |

`塔` 是全形字元，解析器會依東亞字元寬度計算為兩個顯示欄位；編輯地圖時不要任意刪除或增加空格，否則物件可能偏移。

目前解析器不會把 `s`（Speed Up）道具符號轉成資料；雖然遊戲執行邏輯支援速度道具，若要在地圖中配置速度道具，必須先擴充 `scripts/parse_levels.py`，並為解析結果補測試。

## 4. 設計 Boss 方框與關卡資料

在地圖末段使用下列形式標示 Boss 區域：

```text
┌──────┐
│ boss │
└──────┘
```

解析器會尋找 `┌`、`┐`、`└`，計算 Boss 區域的起始列欄、寬度與高度；方框內的其他字元不會再被解析成普通敵人或地形。若一關有多個 Boss，可放置多個方框，解析器會為它們建立多 Boss 資料。

每個關卡檔案結尾應保留 metadata：

```text
第一關魔王：超大珍珠奶茶
背景：台北市遠景
```

解析器會讀取「魔王：」與「背景：」後面的文字，寫入 `bossName` 與 `bgTheme`。真正的 Boss 行為與外觀則由 `js/entities.js` 的 Boss 類別及 `createBoss()` 負責；新增關卡 Boss 時，地圖資料與 Boss 實作要同步完成。

## 5. 配置背景與音樂

每關背景圖片在 `js/game.js` 的 `stageBackgrounds` 陣列中依關卡索引排列。新增關卡時要同時：

1. 將圖片放入 `assets/`。
2. 在 `stageBackgrounds` 加入路徑。
3. 確認圖片能在 800×480 視窗中裁切後辨識場景。

關卡音樂來源是 `docs/levelN.tmd`。修改 TMD 後執行：

```bash
python3 scripts/compile_tmd.py
```

此命令會重新產生 `js/bgmData.js`。該檔案是產物，不應直接編輯；若編譯工具或樂譜格式失敗，應先修正 `.tmd` 或編譯腳本，再重新產生。

## 6. 編譯關卡資料

完成 Markdown 地圖後執行：

```bash
python3 scripts/parse_levels.py
```

成功後會重新產生 `js/levelData.js`，並列出每關解析出的：

- 地形數量
- `x` 敵機數量
- `s` 敵人數量
- 砲塔數量
- 陷阱數量
- Boss 方框數量

如果出現 `No grid rows found`，通常表示地圖行沒有用 `│...│` 包住，或 fenced code block 中的地圖格式被破壞。

## 7. 驗證清單

每次新增或調整關卡後，至少完成以下檢查：

### 結構檢查

- 地圖有起始點 `->`。
- 地圖高度符合目前關卡規格。
- Boss 方框完整，且位於關卡末段。
- 沒有把 `boss` 文字放在方框外。
- 全形 `塔` 的左右空格仍保持對齊。

### 遊戲性檢查

- 玩家從起點能安全移動到第一個挑戰區。
- 每個 `s` 背刺觸發點都有可反應的空間。
- 每個 `|` 陷阱都有預警後的閃避路徑。
- 固體地形沒有造成必死夾擊或無法通過的死路。
- Boss 戰開始前，鏡頭能正常鎖定並顯示警告。
- 道具不會被地形完全遮住，也不會出現在無法抵達的位置。

### 產物與回歸檢查

```bash
python3 scripts/parse_levels.py
node --check js/game.js
node --test tests/mobileExperience.test.mjs
```

重新產生資料後，檢查 `git diff` 是否只包含預期的 `js/levelData.js` 變更。不要手動在產生檔中加入關卡資料；所有可維護的關卡內容都應回到 `docs/levelN.md`。

## 8. 完整交付流程

新增一關時，建議依下列順序交付：

1. 建立 `docs/levelN.md`，先完成地圖節奏與 metadata。
2. 配置或新增背景圖片。
3. 實作或選定 `createBoss()` 對應的 Boss 行為。
4. 建立或更新 `docs/levelN.tmd` 音樂。
5. 執行 `parse_levels.py` 與 `compile_tmd.py`。
6. 在瀏覽器中測試起點、普通敵人、陷阱、道具、Boss 戰與過關流程。
7. 執行語法檢查與測試。
8. 檢查產物 diff，確認沒有手動修改自動產生檔。
9. 將關卡主題、特殊規則與驗證結果記錄在對應的工作紀錄或 Issue 中。

這樣可以讓地圖設計、執行資料、Boss 行為、背景與音樂各自維持清楚的來源，後續接手者也能從 `docs/levelN.md` 重建整個關卡。
